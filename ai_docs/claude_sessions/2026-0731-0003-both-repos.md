# Session: the project backlog becomes a committed file — `init`, the install-time offer, and the plugin-host change that makes it possible

Session ID: `4f37aea1-3489-4178-b3ae-1a753a3ecb71`
Date: 2026-07-31
Repos touched: `cats-todo` and `cats` (sibling)

## The ask

Reverse the previous session's decision: `.cats-todo` **should** be checked in
with all projects. Then, when the plugin is installed, ask whether to
initialize (`init`) local todos — showing the total and a sample of the first
three. Update the README.

Two clarifications came back mid-session and both changed the design:

1. **Fresh install asks; an upgrade does not.** An upgrade re-runs every build
   step, so without a memory the question would be re-asked forever.
2. **The count-and-sample is a guard, not a greeting.** It is what you see when
   `init` is about to wipe an existing backlog — show the first todos and
   confirm before deleting. (My first reading had it as a welcome message for a
   freshly cloned repo, which is wrong: nothing is at stake there.)

## What made this worth an explicit command

A project backlog is now a file in someone's version control. That is the whole
justification for `init` existing rather than letting the first save create it:
adding a tracked file should be a decision, not a side effect. It also makes
`init` the only operation in cats-todo that can destroy todos wholesale — every
other mutation is one todo at a time — so the destructive path got the care.

**This repo stays the exception**, and that took a second decision. The work
was branched off `ebc268b`, where `.cats-todo/todos.json` was gitignored here;
the first pass removed that line and ran `init` on this repo. On push it turned
out `origin/main` had moved 30 commits ahead (v0.4.4 — search box, action bar,
clickable rows, image attachments) and had gone *further* the other way:
`ada8441` widened the ignore to the whole `.cats-todo/` directory, because
attachments land in `.cats-todo/images` and were showing up untracked.

Read carefully, that is not a conflict of intent. `ada8441`'s own comment still
says *"A project backlog is committed with the repo in a normal project (see
README)"* — it is a **dogfooding-scratch** decision about this repo, not a
policy reversal. So the ignore stays, the empty backlog committed in the first
pass was dropped, and the README now names the exception out loud. A backlog
whose prompts are "test the thing I am building" is scratch, not a record, and
its screenshots do not belong in the history.

## The safety contract (`init.go`)

The order is the contract:

```
existing todos → summarize → require an explicit yes → only then write
```

| Situation | Outcome |
|---|---|
| No backlog, or a file with zero todos | created, no ceremony (nothing to lose) |
| Existing todos, terminal, `y` | summary shown, then replaced |
| Existing todos, terminal, bare enter / `n` / `^D` | **kept**, reported, exit 0 |
| Existing todos, **no terminal** | **refuses**, exit 1, backlog untouched |
| `-f` | replaces without asking, terminal or not |

Declining is not an error — it exits 0 and says what it left alone. The refusal
in the no-terminal case is the important one: reading a prompt off a closed
stdin returns EOF instantly, and treating that as an answer is exactly how a
backlog gets deleted by a script nobody thought was answering questions.

The summary is the count plus the first three titles in backlog order — which
is priority order (see `store.move`), so the sample is the top of the list, not
an arbitrary slice:

```
proj already has a backlog: 4 todos
  · fix the flaky reconnect
  · port the drop picker
  · document the socket
  …and 1 more
Replace it with an empty backlog? This deletes those 4 todos. [y/N]
```

`init` resolves the same project root the manager and `add` do, so it works
from any subdirectory. It writes `[]`, not `null` — the file is committed, so
it has to read sensibly in a diff.

## The install-time offer, and how it stays quiet

`cats-todo init --post-install`, wired as a second `[[build]]` step
(`… || true` — an optional convenience must never fail an install).

Fresh-vs-upgrade is a marker file, `.install-offered`, in the global config
dir — the one location shared across every project and every installed copy.
It is written **before** the offer runs, not after: someone who quits at the
prompt has still been asked.

The second half of the rule matters as much: an existing config dir also counts
as "already a user". Anyone who installed before this feature shipped has no
marker but does have that directory, and greeting a long-time user as new would
be noise.

Two things it deliberately will not do:

- **Prompt without a terminal** — it prints how to run `cats-todo init`
  instead.
- **Initialize the plugin's own checkout** — guarded by an `isPluginRoot`
  check, because a build step's working directory *is* the plugin root.

## The cats-side change (sibling repo)

Checking the host first is what turned this from a guess into a design.
`internal/plugin/install.go`'s `runStep` set `cmd.Dir` to the plugin root and
never wired `Stdin` — zero `Stdin` references in the whole package. So an
install-time prompt had **no terminal to read from and no idea which project
you invoked from**. Both had to be fixed in cats.

`runBuild` now calls a new `runBuildStep` that adds exactly two things:

- `CATS_PLUGIN_INSTALL_CWD` — the host process's own working directory, which
  is the user's shell cwd. Nothing else can answer "which project is the user
  in?" from inside a build step.
- stdin, **only when the host has a terminal**. Inherited unconditionally, a
  step that reads stdin would hang a headless or scripted install forever
  instead of seeing the immediate EOF it gets today.

The host's own `git` calls keep the old stdin-less `runStep` on purpose: with a
terminal attached, a private-repo clone would sit at a credential prompt inside
what the user experiences as "catctl is installing", rather than failing fast.

cats-todo reads `CATS_TODO_INSTALL_CWD` first and falls back to the host's
variable, so a wrapper or a hand-run `--post-install` can aim the offer
somewhere without impersonating the host.

## The bug the smoke test caught

The first TTY check copied the char-device test the piped-stdin helpers use:

```go
fi.Mode()&os.ModeCharDevice != 0
```

**`/dev/null` is a character device** — and it is precisely what a child
inherits when its parent leaves stdin unset, i.e. the build-step case this
whole feature targets. So `init < /dev/null` prompted into the void, read EOF,
and declined. The backlog survived (the default is the safe one), but the
loud-refusal path never fired and the message was a lie.

Both repos now ask the kernel instead:

- cats-todo: `term.IsTerminal` — `github.com/charmbracelet/x/term` promoted
  from indirect to a **direct** dependency (already in the module graph via
  bubbletea, so no new download).
- cats: `pty.Getsize(os.Stdin)` — a window-size ioctl, using `creack/pty`,
  already a direct dependency there. No new dep in either repo.

## What the rebase onto v0.4.4 added

Landing on the newer tree brought a feature this work had never seen:
attachments live in `.cats-todo/images/<todo-id>/`. `init`'s replace path threw
away every todo and left those directories orphaned — invisible to the UI, and
committed beside a backlog that no longer references them.

Replace now removes them, **after** the save succeeds and in the same order
`store.delete` uses (a backlog still listing a todo whose images are already
gone is the worse of the two failures). The confirmation grows ", and their
attachments" when any todo owns files — the originals may well be off the
user's Desktop by now, which is the whole point of copying them in.

Conflicts were in `.gitignore` (took upstream's), `README.md` and `main.go`
(both sides kept — the `-i`/image lines and the `init` lines coexist), while
`cats-plugin.toml` auto-merged. Version left at upstream's 0.4.4; this repo
does release bumps in their own `chore(release):` commits.

## Tests

- `init_test.go` (new, 15 tests) — weighted toward the destructive path:
  non-interactive never wipes, bare enter keeps, decline is not an error,
  `-f` skips the prompt, an empty existing backlog needs no confirmation, the
  summary caps at three with `…and N more`, the offer runs once then goes
  quiet, an existing config dir keeps it quiet, host-cwd precedence, the
  plugin-checkout guard, and a replace taking its attachments with it.
- cats `internal/plugin/plugin_test.go` — a build step records `$PWD` and
  `$CATS_PLUGIN_INSTALL_CWD` and the test asserts they are the plugin root and
  the host's cwd respectively.

## Verification on a real PTY

Unit tests cannot prove terminal behavior, and `script -q /dev/null` turned out
to inject `^D` ahead of the piped answer — the accept path looked like a
decline through it. `expect` drove it properly:

- `catctl plugin link` on a fresh install prompts, and names the invoking
  project (`proj2`), not the plugin checkout.
- `y` creates the backlog; a second run prints **nothing**.
- `init` over 4 todos shows the summary, confirms, replaces.
- `init < /dev/null` and `echo y | init` both refuse, exit 1, backlog intact.

## Standing notes

- The offer only becomes a real prompt against a cats build carrying the
  `runBuildStep` change. Against an older host it degrades on its own to
  printing instructions — no version check, no breakage.
- The wire-contract copies in `internal/{app,ctlproto,integration}` are
  unchanged this session.
- Version left at upstream's 0.4.4 — additive command, no incompatible change,
  and releases are their own commits here.
- **Check `git fetch` before building on this checkout.** It sat 30 commits
  behind for this whole session, which is why the ignore question had to be

# Session: the filter line becomes a search box

Session ID: `93aa4588-0db4-4f73-95e2-3f38f8562e35`
Date: 2026-07-30
Released as: `v0.4.4`

One small ask that arrived in three pieces, each one landing mid-turn while the
previous edit was still in flight. The filter line at the top of the list had led
with a bare `❯` since the fuzzyList was adapted from herdr-plus. It reads as a
shell prompt. It is not one — it is the thing you type a search into.

## Ask 1 — the glyph

> "The filter icon `>` should be a magnifier search icon"

The glyph lives in exactly one place, `fuzzylist.view`, which both the todo list
and the drop-target picker render through:

```go
b.WriteString(promptStyle.Render("❯ "))
b.WriteString(l.input.View())
```

The first swap was `⌕` (U+2315). The reasoning was width: a previous session's
notes (`2026-0729-2244-clickable-action-bar.md`) recorded a chip whose two-cell
glyph got clipped to half a cross at a pane edge, so a single-cell magnifier
looked like the safe choice — and a double-width emoji sitting immediately left
of a text input is exactly where a terminal's width miscount would push the
cursor off by a column.

## Ask 2 — chrome

> "And also give me some chrome to show I am in a search box"

## Ask 3 — the glyph, again

> "Oh, that search icon is way too small!"

Correct. `⌕` is technically single-width and visually a speck. Went to `🔍`. The
width worry turned out to be moot for a different reason than expected — see the
fixed field width below.

## What the chrome could not be

The obvious move is a border around the query line. It is the wrong move here,
and the reason is a constraint two sessions old:

```go
// ui.go
const actionBarRow = 4          // header 0, blank 1, filter 2, blank 3, bar 4
const listRowsRow = actionBarRow + 2
const targetRowsRow = 4
```

Mouse hit-testing subtracts these constants from a click's `Y` and hands the
remainder to `fuzzyList.rowAtLine`. Nothing re-measures the frame. A full border
adds a top and a bottom line, the whole list slides down two rows, and every
click lands two todos off — silently, since the arithmetic still "works".

So: **side rails only.** Lipgloss takes per-side border flags, and
`Border(b, false, true)` is top/bottom off, left/right on — a real field edge
that costs zero lines.

```go
searchFieldStyle = lipgloss.NewStyle().
    Border(lipgloss.RoundedBorder(), false, true).
    BorderForeground(lipgloss.Color(colChrome)).
    Padding(0, 1)
```

`colChrome` is the same tone as the raised surface a live action-bar button sits
on, so the field reads as part of the same furniture rather than a new color.

## The rails have to hold still

With the border hugging its content, the box grows and shrinks on every
keystroke — the right rail crawls across the pane as you type. The fix is to give
the input a fixed width, which the list had never set:

```go
const searchFieldWidth = 34
ti.SetWidth(searchFieldWidth)
```

34 columns fits both placeholders (`Type to filter prompts…`,
`Filter targets…`) and still leaves the `n/m` match count beside it in a cats
pane. This also disposes of the emoji-width worry from ask 1: the input pads
itself to a fixed cell count, so whatever the magnifier costs, the right rail
does not move.

The rendered line, ANSI stripped:

```
│ 🔍 Type to filter prompts…            │  1/1
```

## Verifying it

`TestListRowsMatchWhatIsDrawn`, `TestTargetRowsMatchWhatIsDrawn`, and
`TestActionBarRow` all render a real frame and walk it against the constants.
They are precisely the tests that would have caught a full border, and they
passed — which is the actual proof the side-rail choice was right, not just
plausible. Full suite green.

To *see* it, a throwaway `zz_preview_test.go` printed `m.View()` and was deleted
after.

## Running it — the gap

> "run it so I can see it"

Could not. No `tmux` on this machine, so there is no way to launch the TUI,
`send-keys` a query, and `capture-pane` the result. A `script -q /dev/null`
pty run hung on the alt screen and had to be killed. The binary was built to
`bin/cats-todo` and handed back for the user to run.

Worth installing `brew install tmux` — every future UI change in this repo has
the same problem, and it is the difference between showing a frame and
describing one.

## Release

Two commits, the repo's usual shape: the change, then the bump.

```
48e5f85 feat(ui): the filter line is a search box
c88135b chore(release): v0.4.4
```

Version lives in two files that must move together — `main.go`'s `const version`
and `cats-plugin.toml`'s `version`.

One stumble: `git push --follow-tags` pushed nothing, because it only carries
*annotated* tags and `git tag v0.4.4` makes a lightweight one. Every prior tag in
this repo is annotated (`git cat-file -t v0.4.3` → `tag`). Pushed the lightweight
tag, then replaced it with `git tag -f -a` and a forced tag push, seconds later.

The lesson for next time: `git tag -a vX.Y.Z -m "vX.Y.Z"`, and `--follow-tags`
then does the right thing on its own.

## The change

- **`titleUndo`** on the model is a second `promptUndo`, the same type the
  prompt's history uses. `recordUndo` (`ui.go`) snapshots the title before
  routing each message, beside the prompt, and calls `commitTitleEdit`
  afterwards. So the title is recorded by watching, the way the prompt is,
  and no title edit has to remember to snapshot itself. The history is
  emptied in the same three places as `promptUndo`: `backToList`,
  `beginAdd` and `beginEditRef`.
- **The shared rule** moved onto the type so both fields use one copy:
  `promptUndo.commit` (the three outcomes), `back` and `forward` (one undo's
  or redo's move between the stacks), and `restoring` (end the run, set
  `applied`). `undoPrompt`/`redoPrompt` now call these, with the same
  behaviour and notes as before.
- **`titleEditKindOf`** classifies against the textinput's keymap. It has no
  newline case, since enter in the title saves. `ctrl+u` / `ctrl+k`
  (delete before or after the caret) are `editOther`, each its own step.
  Folding a half-title deletion into the surrounding backspaces would make
  one undo overshoot.
- **`undoForm`/`redoForm`** are what the chords now call, and they pick the
  history by focus. The prompt's context menu still calls
  `undoPrompt`/`redoPrompt` directly, since it opens only in the prompt. The
  annotation bar and the flag's note keep no history and say
  "undo works in the title and the prompt".
- The caret is a rune position on both sides: the title's state is
  `Position()`, and it is restored with `SetCursor`, so no walk is needed as
  there is for the prompt.

Design choice: **per-field stacks, not one form-wide stack.** With a shared
stack, cmd+z in the prompt could take back a title typed earlier, out of
sight of the caret. Per-field history is what Mac forms do. Each field's
commit also breaks the other field's typing run, since a key press that
leaves a field's text unchanged ends that field's run. That is the right
reading: switching fields ends a run.

Not covered: the flag's note. It is a third textinput and could get the same
treatment, but its value is mirrored into `formAnnots.FlagNote` in
`forwardForm`, so a restore would also have to write that. Nobody has asked
for it, and it was not raised as an item.

# Session: image attachments on todos — file, screenshot, and clipboard capture

Session ID: `1bf8092c-bfac-4433-a72f-294d97090ac4`
Date: 2026-07-29

## The ask

"What would it take to enable image support in todos?" — an assessment first,
then build it in three phases, each committed on its own.

## The constraint that shaped everything

Established before proposing anything, because it decides what the feature even
*is*: **the drop channel is text-only.** `performDrop` hands the prompt to
`pane.send_input`, which paste-encodes keystrokes into a pane, and the cats
control vocabulary (`internal/app/command_vocab.go`) has nothing that carries
bytes.

So an image never travels as an image. It travels as an **absolute path appended
to the delivered prompt**, and the agent reads the file itself. That reframed the
job from "image support" to "attach files, keep them alive, inline their paths at
drop time" — a much smaller thing than it sounds.

Two format decisions fall straight out of it:

- Paths are **bare, not `@`-prefixed**. `@` starts a file-picker mention in
  Claude Code's input and would rewrite the paste mid-flight.
- The composed text **never ends in a newline** — `sendInput`'s contract is that
  a trailing newline is inserted literally rather than submitting (submission is
  the separate Enter `dropRun` sends).

Header used: `Attached images — read these files:`. A sentence, not a bare
`Images:` label — a path sitting in a prompt reads as a mention, and the agent
has to be told the file is there to be opened.

## Phase 1 — the attachment layer (`images.go`, commit `26fe341`)

`Todo.Images []string` with `omitempty`: a backlog without attachments is
byte-identical to before, and an older binary ignores the field rather than
choking.

Attaching **copies the file into the backlog** — `<backlog>/images/<todo-id>/` —
rather than referencing it. The usual source is a screenshot on the Desktop,
which is exactly the file the user clears out next week. Stored paths are
backlog-relative and forward-slashed (`path.Join`, not `filepath.Join`) so a
committed project backlog survives being cloned elsewhere.

Validation happens **at attach time**, while the user is still standing there:
extension against a known set, regular file, 10 MiB cap. Name collisions get
`-1`, `-2` suffixes, so two files both called `Screenshot.png` stay two
attachments. Attaching is all-or-nothing — a partial copy would leave a todo
carrying some of what was asked for and no sign of the rest.

Two views of the same list, which is the distinction that matters:

- `resolveImages` — display. Reports a file that has gone.
- `imagePaths` — delivery. Leaves it out, rather than sending the agent chasing
  it.

`delete` and `clearDone` remove attachment directories, **saving the JSON
first**: a backlog still listing a todo whose images were already deleted is the
worse of the two failures.

### A call I reversed mid-flight

In the assessment I flagged `store.update`'s field-by-field copy as a gotcha to
fix — "adding `Images` to the struct silently does nothing until you extend that
loop". On implementing it, the opposite was true: `saveForm` sends a `Todo` with
no `Images`, so that whitelist is exactly what **preserves** attachments across a
text edit. Left alone, documented, and pinned by
`TestUpdatePreservesImages`, which sends precisely what the form sends.

Image mutation got its own path instead (`store.setImages`, phase 2), so a caller
that knows nothing about images still cannot blank them.

## Phase 2 — the TUI editor (commit `354f196`)

`ctrl+o` from the edit form opens `stageImages`: a path box plus one row per
attachment. Rows are either **existing** (`rel`, already on the todo) or
**pending** (`src`, an absolute path not yet copied). An add has no todo id to
copy under until it saves, so everything it collects stays pending — and that
turned out to be the right model for edits too.

- `enter` with a path attaches it; `enter` on an empty box means done — the same
  "do what's in front of me" split the list already uses for `enter`.
- `ctrl+r` fills the box with the newest image from `~/Desktop` / `~/Downloads`,
  cycling older on each press. It only *offers* the path, so a wrong guess costs
  nothing. `CATS_TODO_IMAGE_DIR` overrides the folder — we do **not** shell out
  to `defaults read com.apple.screencapture location`.
- `ctrl+x` removes a row. For an existing attachment that is only a *decision*
  until the save, so cancelling the form changes nothing.
- Drag-and-drop works for free: terminals insert the file path on drop.
  `cleanSourcePath` handles what they actually deliver — quoted paths,
  shell-escaped spaces, `file://` URLs, `~`.

`saveForm` copies → records → deletes. Every step leaves the todo either as it
was or as asked for, and a failure anywhere takes that save's own copies back out
with it. `formImagesOrig` is kept because the form's own list records what
*survived*, not what was *there* — `droppedRels` needs both.

### The ctrl+i trap

The obvious mnemonic cannot work. **`ctrl+i` and `tab` are both `0x09`**, and the
form already binds `tab` to field switching — so without the kitty protocol
`ctrl+i` arrives as that tab and the editor never opens. Moved to **`ctrl+o`**
(free in both the app and `textarea`'s default keymap, which claims a, b, d, e,
f, h, k, m, n, p, t, u, v, w). `ctrl+i` stays bound for terminals that can tell
them apart; the footer advertises only `ctrl+o`. Same problem and same shape of
answer as `shift+enter` vs `alt+enter` — see `modEnter`.

Found by driving the program with real terminal bytes, not by reading the code.
That run is now `TestAttachKeysEndToEnd` in `keys_e2e_test.go`, alongside the
enter-bindings one from the previous session. The wire-level test earns its keep
twice now.

Also caught by rendering the screens: informational notes ("removed shot.png")
were coming out in the *error* style, because the editor had a single `imgErr`
channel. Split into `imgStatus` / `imgStatusErr`, mirroring the list's
`status` / `statusErr`.

## Phase 3 — clipboard capture (`clipboard.go`, commit `e7c3537`)

The one capture path that cannot start from a file: an image copied out of a
browser, or `shift+cmd+ctrl+4`, exists only on the pasteboard, and **no terminal
hands clipboard image bytes to the foreground app**. `osascript` asks the system
directly, writing the PNG flavor to a temp file that then joins the form as an
ordinary pending source — same validation, same copy-at-save.

Stored as `clipboard.png`, so the backlog records the picture rather than the
plumbing (`attachOne` takes the basename; a stored `cats-todo-clip-1847.png`
would name the wrong thing).

macOS only, and honest about it: `clipboardImageSupported()` gates both the key
and the footer hint.

`ctrl+v` stays **one key for both kinds of paste**. `clipboardOffer` reads the
pasteboard's flavors — metadata only, never contents — and picks between three
answers:

| Offer | `ctrl+v` does |
|---|---|
| `clipPNG` | capture and attach it |
| `clipUnusableImage` | say macOS won't hand it over as PNG |
| `clipNoImage` | fall through to the input's ordinary text paste |

That middle case exists because silently pasting nothing is the worst possible
outcome in a TUI. In practice macOS synthesizes a PNG flavor for almost anything
image-shaped, so it is rare — but it is the one failure the user could not
otherwise diagnose.

Temp captures are tracked in `model.clipboardDirs` and removed on **every** exit
from the form: after a save copies them in, on cancel, when a fresh form opens
over a stale one, and immediately when their row is removed (nothing else refers
to a capture, so it need not wait).

The call runs **inline in `Update`**, not off the UI thread like a drop — the read
is milliseconds, with a 3s context timeout as the backstop for a wedged
pasteboard server.

### How the osascript path was verified

Exercised once against the real pasteboard, end to end: a 70-byte PNG on, the
same bytes and a valid signature back out, passing `validateImageSource`. The
clipboard was confirmed empty first and restored after — it now holds an empty
string rather than being pristine-empty, which reads as "no image".

The test suite deliberately **does not** repeat that: putting a known image on
the clipboard would clobber whatever the person running `go test` had copied.
`osacompile -o /dev/null` validates the AppleScript grammar (including the
`«class PNGf»` literal and the try/on-error block) without executing it, and
`readClipboardInfo` is table-tested against real `clipboard info` output —
including the two samples captured from that live run.

## Where images show up

- List rows: `📎n` **leads** the description. A prompt written about a screenshot
  usually reads as a fragment without it ("this is wrong"), so the fact that one
  is carried is what makes the row make sense.
- Form: a `📎 1 image — ctrl+o to attach` line, shown even when empty. An editor
  nobody knows about is one nobody uses, and "no images" is also the answer to
  "did my screenshot make it in".
- `ctrl+v` prompt view: a `📎 n attached:` block, with `(missing — will not be
  sent)` on any file that has gone. Plain text, no styling — the whole body goes
  through one lipgloss `Width()` wrap, and pre-styled spans have their ANSI
  resets clobbered at the wrap points.

## Standing notes

- The wire-contract copies in `internal/{app,ctlproto,integration}` stay in
  lockstep with cats. **Unchanged this session** — no wire changes; the feature
  rides entirely on the existing `pane.send_input`.
- **No load-time orphan sweep.** A sweep runs between `reload` and `save`, where
  a concurrent pane could have just written a todo whose images it would delete.
  Deletion cleanup covers the normal case; the only leak left is a crash
  mid-attach.
- **Version not bumped** (still 0.3.0). These are additive — new keys, an
  `omitempty` field, an unchanged wire contract — but a bump to 0.4.0 before the
  next release would be reasonable.
- The size cap (10 MiB) and accepted formats (`.png .jpg .jpeg .gif .webp`) live
  in `images.go` as a const and a map, deliberately easy to widen.
